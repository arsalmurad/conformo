# Decisions

One line of reasoning each, newest last.

- Work in `/home/user/arsalmurad/conformo` cloned read-only (shallow). Push access was declined by the harness and the brief says never push; commits stay local on `upgrade/v0.2`.
- Fetch official corpora with `git clone --depth 1` + tag pin, because GitHub zip/API hosts are blocked here but the git lane works; pins are by commit SHA and recorded in the manifest.
- SchXslt2 is pinned from Maven Central (hash 5251979...), verified against Maven's own published .sha256/.sha1; the earlier Codeberg pin is dropped because Codeberg is unreachable from some networks. (An interim hash I first noted was the body of a rate-limit page; the fetcher's checksum verification caught it, which is the point of pinning.)
- All third-party artefacts are declared once in `tools/artefacts.manifest.json` and fetched by `tools/fetch-artefacts.mjs` (Node, no Python), replacing `tools/fetch_artefacts.py` and the inline URLs in the compile script.
- Git artefacts are pinned by the commit a tag peels to and fetched via `refs/tags/<tag>` because some upstream repos have a branch with the same name as a tag.
- `Invoice.payment` (BG-16) is optional: EN 16931 makes it 0..1 and official corpus documents omit it; `checkInvoice` warns, and XRechnung's own check (BR-DE-1) is left to the KoSIT rules. The README crash was a missing-field TypeError; the fix is a typed `InvoiceInputError` listing every problem.
- `unitPriceMinor` may be fractional (minor units) because BT-146 allows more decimals than the currency; arithmetic stays in exact BigInt decimals, only output formatting changed (`priceToMajor`).
- EN 16931 base rules now come from CEN's own release (validation-1.3.17), not the factur-x pip package's adaptation, per the brief; the pip package is kept pinned only for the French CTC rules and the Factur-X profile XSDs.
- BT-29/BT-46 with a scheme are written as CII `ram:GlobalID` (the EN 16931 binding), without a scheme as `ram:ID`.
- BT-90 (SEPA creditor id) is stored under `payment.directDebit.creditorId` and written as CII `CreditorReferenceID` / UBL seller `PartyIdentification` with schemeID `SEPA`, per the syntax bindings.
- A legal registration id without a scheme (BT-30-1/47-1/61-1) is a warning, not an error: EN 16931 makes the scheme optional, and the conformance run showed that refusing it blocked re-serializing most official sample documents. The invariant that matters is kept: Conformo never writes a default scheme.
- (UX v0.3) "Who is this invoice for?" has four answers, each mapped to one profile and rule-set combination that `packages/compliance-data` lists for that country (de.json B2B: zugferd/xrechnung; B2G: xrechnung; fr.json B2B: factur-x/cii). Countries whose dataset lists none of the formats the app writes (BE Peppol, IT FatturaPA, ES FacturaE, PL KSeF, NL) are named as "not supported yet", never offered, because offering them would claim compliance the app cannot show.
- The fields a profile adds (Leitweg-ID, BG-6 contact, SIREN, BT-23, the BR-FR-05 notices, both electronic addresses) are declared per audience with the official rule that demands them; `test/ui-audience.test.ts` blanks each one and proves the cited rule really fires and lands on that field. Deriving the list from the compiled Schematron alone was not possible: the SEF has assertions, not a list of required fields. The contact fields cite BR-DE-5/6/7, not BR-DE-2, because the test showed BR-DE-2 only fires when the whole group is absent.
- An invoice that fails its profile's rules can still be downloaded, but only as a draft: stamped DRAFT/ENTWURF on every page, with no embedded XML and no Factur-X/XRechnung metadata, so a receiving system can never mistake it for an e-invoice.
- The invoice number is typeable again (people continue numbering from another tool). The gapless local sequence stays the default ("Use next number"), "Numbering" in the More menu continues a sequence from any number, and a number already downloaded on this device gets a warning, not a block (a re-issue of the same invoice is legitimate).
- Intra-EU supply of goods (VAT category K) is not offered in the line VAT list: EN 16931 then also needs the actual delivery date and the deliver-to country (BR-IC-11/12), which the form does not ask for. Reverse charge for services (AE) covers the common freelancer case.
- New standard-rated lines default to the seller country's standard VAT rate (EU-27 table in `packages/ui/src/countries.ts`, from the Commission's VAT rates list) instead of 0 %, which BR-S-05 rejects; a rate the user typed is never overwritten.
- The UI typeface is Work Sans, the family the PDF already embeds: self-hosted from `public/assets/fonts` (no font CDN, offline and private), with tabular figures on all amounts, so the interface and the document share one voice.
- The Phase B visual system (docs/DESIGN.md) was planned and reviewed before the Phase A rewrite and used for it, because the Phase A rewrite replaced every class name anyway; styling the new form twice would have been wasted work. Phase B is then the screenshot critique loop, not a second rewrite.
- Validator page messages reuse the app's field-level English/German wording (`packages/ui/src/validation/messages.ts`) by importing the app's source, so the two pages never word the same rule differently. The KoSIT rule text (German) and the French CTC text stay visible as secondary text with the rule id.
- The docs site renders this repository's own Markdown (`docs/site/*.md`, `docs/GERMANY-2027.md`, `docs/CONFORMANCE.md`) with a small hand-rolled renderer instead of adding a Markdown dependency: the site is a few static pages, and rendering the very files the tests execute is what guarantees every sample on it runs. `js` samples run through `tools/doctest.mjs`; bash, curl, JSON and MCP-config samples through `test/docs-site-samples.test.ts`, which fails on any sample line it has no runner for. The long existing references (`docs/cli.md`, `docs/server.md`) are linked, not rendered, because some of their samples need Docker, jq or base64 and cannot run in a test on every platform.
- The KoSIT 86/86 and 28/28 figures on the docs site are parsed from the generated `docs/CONFORMANCE.md` at build time, never typed in, so they cannot go stale.
- `@conformo/core` alone is released as 0.2.1 for the checkInvoice runtime type checks: it is the only library package whose published code changed, and every dependent declares `^0.2.0`, so republishing the other ten packages would ship identical code under new numbers.
